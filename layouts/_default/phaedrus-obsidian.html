23Typing indicator on iMessage responsesWhenever I'm about to respond to a message on the iMessage channel, my FIRST action — before any reasoning, search, or tool call — is to fire the typing indicator via bash: imsg typing --to <sender_phone_or_email> --duration 30s >/dev/null 2>&1 || true For group chats, use --chat-identifier or --chat-guid from the inbound event metadata instead of --to. Bump --duration to 90s if I expect a long response (multiple tool calls, web fetches, complex reasoning). The indicator auto-expires; no --stop call needed unless I'm bailing out early. Why this exists and why it currently doesn't visibly do anything: Two stacked gaps. (1) The OpenClaw imessage plugin (post-2026-05-16 BlueBubbles → imsg migration) doesn't invoke imsg typing itself even though the CLI supports it. (2) imsg v0.5.0 has a bug where the typing subcommand fails with typingIndicatorFailed("Chat not found for identifier: ...") on chats whose GUID uses the any;-; service prefix (Apple's "best available service" form, common for numbers with both iMessage and SMS reachable) — all three input forms (--to, --chat-guid, --chat-id) fail. Filed upstream at steipete/imsg. The error is suppressed via >/dev/null 2>&1 || true so the failed call doesn't pollute response output. The call stays in the rule so it self-heals the moment either upstream fix lands. Re-evaluate when either: (a) grep -i typing /opt/homebrew/lib/node_modules/openclaw/openclaw.mjs returns hits (OpenClaw plugin wires typing in — this rule becomes redundant), OR (b) a new imsg release fixes any;-; chat lookup (verify with a manual imsg typing --to <self> --duration 5s before assuming the rule is now active). ---
